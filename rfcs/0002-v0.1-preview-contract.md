# RFC 0002 Reproducible v0.1 preview contract

Status: proposed
Author: OEMS technical review assisted by Codex
Affected draft version: v0.1
Reviewed baseline: commit 9126bfa
Review date: 2026-10-09

## Problem

The initial fixtures have consistent arithmetic, but the draft does not yet specify enough evidence and population rules for independent implementations to agree on less complete inputs. This RFC records a technical review of RFC 0001, all five metric definitions, schemas, examples and fixtures. It proposes decisions for a preview; it does not accept RFC 0001 or change existing requirements.

## Proposed rules

These are recommendations for discussion. Acceptance must be recorded before applying them to specification text, schemas, fixtures and expected outputs together.

1. **Bound the first preview to reconciled snapshots.** Require a dataset-level declaration that records represent evidence available at evidence_cutoff. Include only revisions observed by that cutoff. Keep historical deployments needed for first-deployment detection. Treat restoration learned after cutoff as unavailable in that snapshot, leaving the episode open. Defer envelope/revision conformance to a separately identified profile rather than imply it is covered by metric cases. F3, F8.
2. **Define one production rollout per service.** Use a canonical service rollout identity; subordinate region, tenant and job outcomes cannot create additional counted deployments. Recommend effective_at be the earliest confirmed instant the changed version/configuration affects the service's production consumers. Later rollout failure does not erase production effectiveness. Specify handling of dark releases, canaries and rollback as examples before accepting this rule. F1.
3. **Represent unresolved qualification coverage explicitly.** Do not infer a window from observed_at or discard records with null effective_at. Require declared scope/time coverage for unresolved records; if coverage overlaps the requested service/window or cannot be bounded, disclose it and keep the affected population provisional. F2.
4. **Separate link coverage from history coverage.** Declare whether change linkage is complete for each qualifying deployment. An empty list with complete linkage means no new commit observations; an empty list with unknown linkage makes lead-time coverage provisional. Define change identity by namespaced repository identity plus commit identity, and reject conflicting aliases instead of double-counting. Keep the first qualifying deployment per change/service as the observation unit. Unknown history cannot establish a first deployment; disclose candidate observations separately from confirmed first-deployment observations. F4.
5. **Define classifications with reviewable evidence.** failed means a qualifying production deployment required immediate intervention such as a rollback or corrective hotfix because of its production impact. incident_driven means the deployment was unplanned and undertaken to remediate a production incident. Scheduled follow-up work is not automatically rework. Record a classification-specific source or review reference; a generic pipeline link alone does not demonstrate either decision. Define what immediate intervention means operationally without inventing a universal elapsed-time threshold. F5.
6. **Define recovery eligibility and quality separately.** Require a causal deployment for the same service, qualifying and classified failed; require onset no earlier than causal production effectiveness and restoration no earlier than onset. Retain the failure-onset cohort, explicitly an OEMS policy. Report completed, open, approximate and unresolved episode counts. Keep the completed-episode median separate from coverage/completion quality; do not label it a complete population measurement when known eligible episodes remain open or eligibility evidence is unresolved. Decide whether approximate episodes enter the main median or a separate statistic before implementing. F6.
7. **Define metric-specific status precedence.** Unresolved population/coverage yields provisional, including an observed empty set; complete known population with no eligible observations yields no_observations; otherwise complete applies only to the declared metric's evidence requirements. Preserve observed numerators and denominators. Label classification bounds as bounds on the observed qualifying population when collection is incomplete, and provide no settled full-population ratio. Apply coverage quality to duration statistics too. F7.
8. **Publish dataset and result contracts.** Add schemas for snapshot metadata and results, including service, window, timezone, cutoff, profile, counts, quality reasons and ratio population scope. Validate start<end, positive and consistent calendar_days, references, service consistency, timestamp order and natural-key conflicts in a separate semantic layer. Include context in expected outputs or define an explicit enclosing result envelope; consumers must not reconstruct it from a filename. F8.
9. **Restrict the first preview's calendar profile.** Recommend UTC whole-day windows only, with matching UTC midnight boundaries and validated calendar_days. Reject unsupported windows explicitly. Retain half-open boundaries: start included, end excluded. Add arbitrary timezones/partial-day windows through a later profile with tests. F9.

## Examples and counterexamples

- **Region fan-out:** one rollout changes regions A and B at different times. It contributes one service deployment, not two; first exposure versus completion must be a recorded policy.
- **No change versus no evidence:** a configuration-only rollout with confirmed empty commit linkage has no lead-time sample. A rollout whose collector cannot retrieve commits has missing evidence, not a zero-second duration.
- **Window boundaries:** a deployment effective exactly at start counts; one effective exactly at end does not. A causal deployment can precede the recovery window if failure onset falls inside it, subject to the accepted cohort rule.
- **As-of recovery:** with cutoff October 12, a restoration observed October 13 cannot retrospectively close the October 12 snapshot. A later snapshot can revise the result with its own cutoff.
- **Incomplete observation:** 1 failed deployment among 2 observed deployments with incomplete source coverage produces an observed ratio, not a known population ratio of 0.5.
- **Classification independence:** a planned deployment can fail without being rework; an unplanned incident hotfix can be rework without failing. A scheduled improvement after an incident is not necessarily rework.

## Alternatives

- Accept the current draft and leave these rules implementation-specific. This prevents an interoperability claim because matching inputs can yield different counts, populations and quality states.
- Require a full event ingestion/reconciliation profile immediately. This would address snapshot construction but expands the first milestone; a bounded reconciled-snapshot profile can be validated first.
- Support every reporting timezone and partial window immediately. This is useful but requires calendar validation, DST examples and an explicit frequency denominator policy before publication.
- Fail every dataset with missing evidence. This is simpler but loses the draft's intentional distinction between invalid relationships and valid incomplete evidence. Prefer explicit quality reasons and scoped provisional outputs, with rejection for contradictions.

## Compatibility and migration

There is no released contract to preserve. Acceptance will change draft metadata and expected outputs, and may add classification/linkage evidence fields. Update prose, schemas, examples and fixtures in one coordinated change. Do not silently reinterpret existing empty change lists as complete linkage. Pin implementations to the exact draft commit until a versioned preview is published.

## Privacy and security implications

Use synthetic fixtures and minimal namespaced identifiers/evidence references. Do not require personal contributor identity, private payloads or publicly accessible incident URLs. Evidence references must be reviewable by authorised consumers; validators must not fetch arbitrary source URLs. Snapshot retention, correction and privacy deletion still need a separately recorded policy; this RFC does not resolve that RFC 0001 question.

## Conformance and verification

Review checks can be reproduced with:

```sh
python -m pip install 'jsonschema[format]==4.26.0'
python tools/review_v0_1.py
```

The script validates five schemas, 39 records/payloads, selected baseline reference/order constraints and all numeric metric fields in the three original cases. It checks ratio statuses, but does not establish that duration/frequency statuses prove evidence completeness. It also demonstrates four shape-valid counterexamples: restoration beyond cutoff, cross-service causality, onset preceding the causal deployment, and unknown qualification with no effective time. It is a review of the original fixtures, not an independent full implementation or conformance engine. Run it without Python optimisation, because it uses assertions.

Before a preview, add accepted-rule cases for:

- Duplicate-identical records, conflicting IDs and aliases of one repository/commit.
- Start/end boundaries, production-effective failure, excluded attempts and one rollout with subordinate outcomes.
- Unknown qualification with/without time bounds, incomplete collection and observed-empty incomplete data.
- Repeat deployment of one change before/inside the window, multiple services, incomplete history, unresolved links and confirmed configuration-only changes.
- Completed/open/approximate recovery, recovery crossing the reporting window/cutoff, shared incidents and invalid causal relationships.
- Independent failure/rework classifications and scheduled post-incident work.
- Invalid dataset metadata, missing output context and explicit rejection of unsupported calendar profiles.

Keep structural validation, semantic rejection/quality handling and calculation comparisons as separately reported checks. Only then add CI for those layers. Passing the present review script is not a certification or preview release gate by itself.

## Open questions

1. Does earliest confirmed production exposure define effectiveness, including canaries? What evidence distinguishes a dark release?
2. How should unresolved qualification coverage and per-deployment change-link completeness be encoded?
3. Do approximate recovery starts enter the main median, and what quality label should apply?
4. Is the reconciled-snapshot, UTC whole-day scope sufficient for the first preview?
5. How should adapters document immediate-intervention decisions and classification evidence consistently?
